# M1 · 存储与幂等（B1a）

对应 issue [#20](https://github.com/xingxue-ux/unwritten-diary/issues/20) · 日期 2026-09-27 · 执行人 xingxue-ux

记录这一片定下来的、会影响后续实现的决定。代码在 `crates/diary_core/`。

## 定下的决定

| 决定 | 理由 |
|---|---|
| 乐观锁以 `captures.revision` 作为聚合根版本 | 记录是聚合根。像「改原始文字」这种改来源的操作也推进它，调用方只需要记住一个版本号 |
| 非草稿状态调用 `save_draft` → `invalid_state` | 契约 2.1 规定草稿正文仅在 draft 阶段可变。静默接受会让「提交后又被改写」变得不可追溯 |
| 新增 `not_found` 与 `invalid_state` 两个错误码 | 契约第 7 节原本没有这两个必需状态。已按流程**先改契约文档与 Dart 枚举，再改实现**，见契约 7 节与 `packages/diary_api` 的 `DiaryErrorCode` |
| `day_key` 由调用方给出的偏移计算 | 契约 1.2 要求按 `diaryTimeZone` 计算。B1a 先接收平台给出的当时偏移；用 IANA 时区名去解析**历史时刻**的偏移（导入路径需要）还没做 |
| 空白草稿提交时不创建空的原始文字版本 | 避免库里出现空 source；有内容才建 `source_items` + `source_revisions` |
| `journal_mode=WAL` + `synchronous=FULL` | 「提交了就是落盘了」是 durable 承诺的前提。`NORMAL` 会在进程崩溃时丢掉最后几个事务，与契约 1.2 的 durable 语义不符 |
| 域事件与业务写入放在同一个事务里 | 防止任务书 3.2 节点名的故障：资料已保存但事件/任务永远丢失 |
| 幂等回执存「请求指纹 + 结果 JSON」 | 重复提交返回原结果；同一个 operationId 换了内容报 `idempotency_conflict`。指纹用 sha256，字段间有分隔符，避免拼接歧义 |
| 索引与派生内容不进 v1 schema | `extracted_contents`、`searchable_chunks` 随 B1b/B2 一起进来，先不给它们留空表 |

## 验证到了什么

`cargo test -p diary_core` 16 项（另有 2 项 support 单测）。其中值得点名的：

- **重复提交不重复写**：同一个 operationId 提交两次，返回结果相同、`revision` 不再推进、来源不重复。
- **同 ID 换内容报冲突**：`idempotency_conflict`。
- **版本过期不覆盖**：`revision_conflict`，且用户原有的内容保留在库里。
- **草稿不制造永久版本**：连续 5 次保存草稿，提交后只有 1 个原始文字版本。
- **重启后数据仍在**：文件库关闭再打开，记录、来源与事件都在。
- **写满走对错误码**：把资料库页数上限压到 2 页造出 `SQLITE_FULL`，错误落到 `storage_full`，且已确认的记录不受影响。

## 没有做到的

- **不是真的满盘测试**：没有 root 权限造不出真实磁盘满，用的是 SQLite 页数上限走同一条 `SQLITE_FULL` 路径。真实磁盘满、磁盘权限变化还没验证。
- **IANA 时区解析没做**：跨午夜的 `day_key` 是按调用方给的偏移算的（已测），但拿一个 IANA 时区名去解析历史时刻的偏移（导入旧材料时必然遇到）还没实现，需要时区数据库。
- **没有崩溃注入**：`synchronous=FULL` 的落盘承诺是配置层面的推理，没有用真实的 kill -9 去验证「提交后立刻断电也还在」。
- **桥接没接线**：`crates/diary_bridge` 还没有暴露这里的方法，前端/桥接暂时调不到。
- 原件文件库、录音会话、队列、提取与索引都还没有（B1b/B1c/B2）。
